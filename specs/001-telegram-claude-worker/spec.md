# 기능 명세서: 텔레그램 기반 원격 Claude 워커 시스템

**기능 브랜치**: `001-telegram-claude-worker`
**생성일**: 2025-11-08
**상태**: 초안
**입력**: 사용자 설명: "이 프로젝트는 "랜디"가 원격환경에서 자가의 LLM 모델과 함께 일하기 위하여 구축하는 프로젝트로 아래와 같은 기능을 포함한다. - 랜디는 텔레그램으로 "Claude agent SDK로 구현한 application" (이하 ccw, claude-code-worker)를 이용해 인공지능과 소통한다. - 즉 텔레그램이 클로드 데스크탑 같은 역할을 한다고 볼 수 있다..."

## 개요

랜디는 텔레그램을 통해 AI 에이전트에게 작업을 위임하여 다른 장소에서 소프트웨어 프로젝트를 계속 진행할 수 있는 원격 개발 보조 시스템이 필요합니다. 이 시스템은 원격 Claude Desktop 역할을 하며, 랜디가 개발 지시를 내리고 완성된 작업을 버전 관리 통합과 함께 받을 수 있게 합니다.

- Q: 단일 작업 실행에 대한 최대 시간 제한은 어떻게 설정할 것인가? → A: 30분 후 자동 종료
- Q: 작업이 진행 중일 때 랜디가 새로운 작업 요청을 보내면 시스템이 어떻게 처리해야 하나? → A: 새 요청 거부, "작업 진행 중" 메시지 반환

- Q: 화이트리스트에 없는 사용자가 봇에 메시지를 보내면 어떻게 되는가? → A: "권한 없음" 메시지 전송 후 무시
- Q: 작업 진행 중에 서버가 재시작되면 진행 중이던 작업의 부분 변경사항을 어떻게 처리하나? → A: 그대로 유지 (Git 미커밋 상태, 랜디가 수동 확인)
- Q: "작업 진행 중" 메시지에 현재 작업의 진행 상태나 예상 완료 시간이 포함되나? → A: 포함 안 함 (간단히 "작업 진행 중" 메시지만)
- Q: 환경 변수에 화이트리스트 사용자 ID가 설정되지 않았으면 시스템이 어떻게 동작하나? → A: 시스템 시작 실패 (에러 메시지 출력)
- Q: 작업이 30분 타임아웃에 도달하면 시스템이 부분 변경사항을 어떻게 처리하나? → A: 작업 로그에 변경 내용 기록 후 Git 미커밋 상태로 유지, "타임아웃"으로 중단되었음을 작업 로그에 명시
- Q: 작업이 실행 중간에 명확화가 필요할 때 CCW가 어떻게 동작하나? → A: 작업 중단, 그간 작업 내용을 로그에 기록, "~한 부분이 애매해서 랜디에게 질문함" 명시, 텔레그램으로 질문 전송 후 응답 대기
- Q: 타임아웃 직전에 랜디가 새로운 작업을 보내면 어떻게 되나? → A: "작업 진행 중" 메시지 반환, 새 요청 거부
- Q: 머지 리퀘스트 생성 중 GitHub 인증이 실패하면 어떻게 되나? → A: 에러 메시지 텔레그램 전송, 작업 실패
- Q: 작업 로그가 합리적인 토큰 예산을 초과하면 시스템이 어떻게 처리하나? → A: 새 로그 파일로 분리
- Q: 마지막 2개의 작업 로그에 상충되는 정보가 포함되어 있으면 어떻게 되나? → A: 랜디에게 명확화 질문
- Q: 작업 로그 파일이 손상되거나 삭제되면 어떻게 되나? → A: 빈 로그 파일 자동 생성 후 진행

## 사용자 시나리오 및 테스트

### 사용자 스토리 1 - 텔레그램을 통한 원격 작업 실행 (우선순위: P1)

랜디가 텔레그램을 통해 Claude Code Worker(CCW) 에이전트에게 개발 작업 지시를 보냅니다. 에이전트는 지시를 받아 원격 서버에서 요청된 개발 작업을 수행하고, 완료 내용을 랜디에게 보고합니다.

**우선순위 이유**: 원격 개발 작업을 가능하게 하는 핵심 기능입니다. 이것 없이는 전체 시스템이 가치가 없습니다.

**독립 테스트**: 텔레그램으로 간단한 작업 지시(예: "main.py에 주석 추가")를 보내고, 에이전트가 작업을 완료하고 확인 응답을 보내는지 검증하여 완전히 테스트할 수 있습니다.

**수락 시나리오**:

1. **Given** 랜디가 회사에 있고 CCW 서버가 실행 중일 때, **When** 랜디가 "로그인 함수에 에러 처리 추가"를 보내면, **Then** CCW가 작업을 수행하고 변경 사항 요약으로 응답함
2. **Given** 랜디가 집에서 프로젝트를 GitHub에 푸시했을 때, **When** 랜디가 회사에서 텔레그램으로 작업 지시를 보내면, **Then** CCW가 프로젝트를 가져와 작업을 수행하고 코드베이스를 업데이트함
3. **Given** CCW가 유휴 상태일 때, **When** 랜디가 작업 지시를 보내면, **Then** CCW가 5초 이내에 수신을 확인하고 실행을 시작함
4. **Given** CCW가 작업을 실행 중일 때, **When** 랜디가 새로운 작업 요청을 보내면, **Then** CCW가 "작업 진행 중" 메시지를 반환하고 새 요청을 거부함

### 사용자 스토리 2 - 작업 세션 컨텍스트 관리 (우선순위: P1)

시스템은 새 작업을 시작하기 전 마지막 2개의 작업 로그를 읽어 여러 작업 세션에 걸쳐 자동으로 컨텍스트를 유지합니다. 이를 통해 랜디는 컨텍스트를 다시 설명하지 않고 멀티 세션 프로젝트를 계속할 수 있습니다.

**우선순위 이유**: 멀티데이 프로젝트와 연속성 유지에 필수적입니다. 컨텍스트 관리 없이는 랜디가 모든 작업마다 전체 컨텍스트를 제공해야 합니다.

**독립 테스트**: 세션 1에서 특정 결정사항이 문서화된 작업 A를 수행한 후, 세션 2에서 작업 A의 컨텍스트에 의존하는 작업 B를 수행하고, CCW가 이전 결정사항을 올바르게 참조하는지 검증하여 테스트할 수 있습니다.

**수락 시나리오**:

1. **Given** CCW가 작업 로그가 문서화된 2개의 이전 작업을 완료했을 때, **When** 랜디가 새로운 관련 작업을 할당하면, **Then** CCW가 마지막 2개의 작업 로그를 읽고 관련 컨텍스트를 새 작업에 적용함
2. **Given** 이전 세션에 특정 아키텍처 결정이 문서화되었을 때, **When** 랜디가 관련 기능을 요청하면, **Then** CCW가 명확화를 요청하지 않고 확립된 패턴을 따름
3. **Given** 이전 작업 로그가 없을 때, **When** 랜디가 첫 작업을 할당하면, **Then** CCW가 로그를 읽지 않고 진행하며 첫 로그 항목을 생성함

### 사용자 스토리 3 - 작업 로그 문서화 (우선순위: P1)

각 작업 완료 후, CCW는 수행한 작업, 내린 결정, 발생한 이슈, 랜디와의 논의를 문서화하는 마크다운 형식의 작업 로그를 자동으로 생성하거나 업데이트합니다. 로그는 이슈별로 구성되며 토큰 비용을 최소화하기 위해 간결하게 유지됩니다.

**우선순위 이유**: 컨텍스트 연속성과 비용 효율성에 필수적입니다. 작업 로그는 P2(컨텍스트 관리)를 가능하게 하는 메커니즘입니다.

**독립 테스트**: 단일 작업을 완료하고 수행한 작업, 내린 결정, 발생한 이슈에 대한 섹션이 포함된 마크다운 로그 파일이 생성되는지 검증하여 테스트할 수 있습니다.

**수락 시나리오**:

1. **Given** CCW가 작업을 완료했을 때, **When** 작업이 종료되면, **Then** CCW가 작업 세부사항, 결정사항, 이슈, 논의 요약이 포함된 마크다운 작업 로그를 생성함
2. **Given** 이슈 #123에 대한 기존 작업 로그가 있을 때, **When** CCW가 동일한 이슈에 대한 다른 작업을 완료하면, **Then** CCW가 새 파일을 생성하는 대신 기존 로그에 추가함
3. **Given** CCW가 작업을 문서화하고 있을 때, **When** 로그를 생성하면, **Then** 로그가 간결하면서도 다음 에이전트 세션이 작업을 계속하기에 충분한 세부사항을 포함함
4. **Given** 여러 작업 세션이 발생했을 때, **When** 랜디가 로그를 검토하면, **Then** 각 로그가 관련된 이슈를 명확하게 식별함

### 사용자 스토리 4 - 버전 관리 통합 (우선순위: P2)

랜디의 명시적 명령에 따라, CCW는 완료된 작업을 버전 관리에 커밋하고 GitHub에 머지 리퀘스트를 생성합니다. 랜디는 변경사항을 검토하고 머지할 수 있으며, 이는 GitHub Actions를 통한 자동 배포를 트리거합니다.

**우선순위 이유**: 적절한 개발 워크플로우에 중요하지만 기본 작업 실행보다는 부차적입니다. 처음에는 수동 커밋으로 테스트할 수 있습니다.

**독립 테스트**: 작업을 완료하고, 텔레그램으로 커밋 명령을 내리고, GitHub에 커밋과 머지 리퀘스트가 나타나는지 검증하여 테스트할 수 있습니다.

**수락 시나리오**:

1. **Given** CCW가 작업을 완료했을 때, **When** 랜디가 "이 작업 커밋해"를 보내면, **Then** CCW가 설명이 포함된 커밋 메시지로 커밋을 생성하고 기능 브랜치에 푸시함
2. **Given** CCW가 커밋을 생성했을 때, **When** 랜디가 "머지 리퀘스트 생성"을 보내면, **Then** CCW가 작업 요약과 함께 GitHub에 머지 리퀘스트를 생성함
3. **Given** 랜디가 머지 리퀘스트를 머지했을 때, **When** 머지가 완료되면, **Then** GitHub Actions가 서버로의 배포를 트리거함
4. **Given** GitHub Actions 배포가 완료되었을 때, **When** 배포가 성공하면, **Then** CCW가 텔레그램으로 "배포 성공" 알림을 보냄
5. **Given** GitHub Actions 배포가 실패했을 때, **When** 실패가 감지되면, **Then** CCW가 텔레그램으로 실패 원인과 함께 "배포 실패" 알림을 보냄
6. **Given** CCW가 커밋하려고 할 때, **When** 명시적 커밋 명령이 주어지지 않았으면, **Then** CCW가 자동으로 커밋하지 않음

### 사용자 스토리 5 - 안전한 원격 서버 명령 실행 (우선순위: P3)

랜디는 텔레그램을 통해 안전한 서버 명령을 실행할 수 있습니다. 시스템은 파괴적 명령(rm, 시스템 설정 쓰기)과 콘솔 출력을 반환할 수 없는 대화형 명령(vi)을 차단합니다.

**우선순위 이유**: 유용한 유틸리티 기능이지만 핵심 개발 워크플로우에는 중요하지 않습니다. 기본 작업 실행이 작동한 후 추가할 수 있습니다.

**독립 테스트**: 텔레그램으로 허용된 명령(ls, cat)과 차단된 명령(rm, vi)을 보내고 올바른 실행 또는 설명 메시지와 함께 차단되는지 검증하여 테스트할 수 있습니다.

**수락 시나리오**:

1. **Given** 랜디가 서버 상태를 확인하고 싶을 때, **When** 랜디가 "명령 실행: ls -la"를 보내면, **Then** CCW가 명령을 실행하고 콘솔 출력을 반환함
2. **Given** 랜디가 파괴적 명령을 보냈을 때, **When** 랜디가 "명령 실행: rm -rf /"를 보내면, **Then** CCW가 명령을 차단하고 실행할 수 없는 이유를 설명함
3. **Given** 랜디가 대화형 명령을 보냈을 때, **When** 랜디가 "명령 실행: vi config.txt"를 보내면, **Then** CCW가 명령을 차단하고 대안적 접근 방식을 제안함
4. **Given** 랜디가 시스템 설정 쓰기 명령을 보냈을 때, **When** 명령이 감지되면, **Then** CCW가 실행을 차단하고 랜디에게 알림

## 요구사항

### 기능 요구사항

- **FR-001**: 시스템은 텔레그램을 통해 랜디로부터 작업 지시를 받아야 함
- **FR-002**: 시스템은 환경 변수에 저장된 화이트리스트 텔레그램 사용자 ID와 비교하여 들어오는 메시지를 인증해야 함. 화이트리스트가 설정되지 않으면 시스템 시작 시 에러 메시지를 출력하고 종료해야 함
- **FR-003**: 시스템은 화이트리스트에 없는 사용자 ID로부터의 메시지를 거부하고 "권한 없음" 메시지를 전송한 후 무시해야 함
- **FR-004**: 시스템은 Claude Agent SDK를 사용하여 개발 작업을 실행해야 함
- **FR-005**: 시스템은 작업 실행 중에 새로운 작업 요청을 받으면 거부하고 간단한 "작업 진행 중" 메시지를 텔레그램으로 반환해야 함 (진행 상태나 예상 완료 시간 포함 안 함)
- **FR-006**: 시스템은 한 번에 하나의 작업만 실행해야 함
- **FR-007**: 시스템은 각 작업 완료 후 마크다운 작업 로그를 생성하거나 업데이트해야 함
- **FR-008**: 작업 로그는 리포지토리 내 `.ccw/logs/` 디렉토리에 저장되며 Git으로 추적되어야 함. 로그 파일이 손상되거나 삭제된 경우 빈 로그 파일을 자동 생성하고 작업을 계속해야 함
- **FR-009**: 작업 로그는 논의, 내린 결정, 잘못된 가정, 발생한 이슈, 수행한 작업을 포함해야 함
- **FR-010**: 시스템은 작업 로그를 이슈별로 구성하고, Claude가 작업이 동일한 이슈에 속한다고 판단하면 기존 로그에 추가해야 함
- **FR-011**: 시스템은 새 작업을 시작하기 전에 컨텍스트를 설정하기 위해 마지막 2개의 작업 로그를 읽어야 함. 로그에 상충되는 정보가 있으면 랜디에게 명확화 질문을 해야 함
- **FR-012**: 작업 로그는 토큰 비용을 최소화하기 위해 간결해야 하지만 후속 에이전트 세션에 충분한 세부사항을 제공해야 함. 로그가 합리적인 토큰 예산을 초과하면 새 로그 파일로 분리해야 함
- **FR-013**: 시스템은 랜디의 명시적 명령이 있을 때만 완료된 작업을 버전 관리에 커밋해야 함
- **FR-014**: 시스템은 랜디의 명시적 명령이 있을 때만 GitHub 머지 리퀘스트를 생성해야 함. GitHub 인증이 실패하면 에러 메시지를 텔레그램으로 전송하고 작업을 실패 처리해야 함
- **FR-015**: 시스템은 텔레그램을 통해 랜디에게 작업 완료 알림을 보내야 함
- **FR-016**: 시스템은 텔레그램을 통해 안전한 서버 명령을 받고 실행해야 함
- **FR-017**: 시스템은 rm 및 유사한 복구 불가능한 작업을 포함한 파괴적 명령을 차단해야 함
- **FR-018**: 시스템은 시스템 설정 쓰기 명령을 차단해야 함
- **FR-019**: 시스템은 콘솔 출력을 반환할 수 없는 대화형 명령(예: vi, nano)을 차단해야 함
- **FR-020**: 시스템은 실행된 서버 명령의 콘솔 출력을 텔레그램을 통해 랜디에게 반환해야 함
- **FR-021**: 시스템은 머지 후 배포를 위해 GitHub Actions와 통합되어야 함
- **FR-022**: 시스템은 GitHub Actions 배포 상태를 모니터링해야 함
- **FR-023**: 시스템은 배포 성공 또는 실패 시 텔레그램을 통해 랜디에게 알림을 보내야 함
- **FR-024**: 배포 실패 알림은 실패 원인 정보를 포함해야 함
- **FR-025**: 작업 실행 중 명확화가 필요한 경우, 시스템은 작업을 중단하고 그간의 작업 내용을 작업 로그에 기록해야 하며, "~한 부분이 애매해서 랜디에게 질문함"을 명시한 후 텔레그램으로 질문을 전송하고 응답을 대기해야 함

### 비기능 요구사항

- **NFR-001**: 단일 작업 실행은 30분 후 자동으로 종료되어야 함
- **NFR-002**: 작업이 타임아웃되면 시스템은 텔레그램을 통해 랜디에게 타임아웃 알림을 보내야 함
- **NFR-003**: 타임아웃된 작업의 부분 변경사항은 Git 미커밋 상태로 유지되어야 하며, 작업 로그에 변경 내용과 진행 상태를 기록하고 "타임아웃"으로 중단되었음을 명시해야 함
- **NFR-004**: 서버 재시작 시 진행 중이던 작업은 자동으로 중단되며, 부분 변경사항은 Git 미커밋 상태로 유지됨. 서버 재시작 후 랜디에게 중단 사실을 알려야 함
- **NFR-005**: 중단된 작업의 정보(시작 시간, 중단 시간, 중단 이유)는 작업 로그에 기록되어야 함

### 주요 엔티티

- **작업 지시**: 수행할 작업에 대한 설명을 포함하는 랜디의 개발 작업 요청
- **작업 로그**: 특정 이슈에 대한 작업 실행 세부사항, 결정사항, 이슈, 논의를 포착하는 마크다운 문서. 리포지토리의 `.ccw/logs/` 디렉토리에 저장되며 Git으로 추적됨
- **에이전트 세션**: CCW가 하나의 작업 지시를 처리하는 단일 실행 컨텍스트로, 이전 작업 로그에 액세스할 수 있음
- **서버 명령**: 원격 서버에서 실행될 명령줄 지시로, 안전 제한이 적용됨
- **이슈**: 공통 작업 로그를 공유하는 관련 작업의 논리적 그룹

## 성공 기준

### 측정 가능한 결과

- **SC-001**: 랜디가 텔레그램으로 작업 지시를 보내고 10초 이내에 작업 시작 확인을 받을 수 있음
- **SC-002**: 개발 작업의 95%가 추가 명확화 없이 성공적으로 완료됨
- **SC-003**: 작업 로그에 충분한 컨텍스트가 포함되어 후속 작업의 90%가 이전 결정사항을 다시 묻지 않고 진행할 수 있음
- **SC-004**: 시스템이 위험한 명령 시도(rm, 시스템 쓰기, 대화형 명령)의 100%를 성공적으로 차단함
- **SC-005**: 랜디가 작업 로그를 기반으로 올바른 컨텍스트가 적용된 멀티 세션 프로젝트를 계속할 수 있음
- **SC-006**: 작업 로그 저장의 토큰 비용이 평균 로그 항목당 2000 토큰 미만으로 유지됨
- **SC-007**: CCW가 생성한 머지 리퀘스트에 정확한 작업 요약이 포함되어 랜디가 2분 이내에 변경사항을 검토할 수 있음
- **SC-008**: 안전한 서버 명령이 실행 후 30초 이내에 콘솔 출력을 텔레그램으로 랜디에게 반환함
- **SC-009**: 배포 완료 시 랜디가 5분 이내에 배포 결과(성공/실패) 알림을 받음
- **SC-010**: 배포 실패 알림이 문제 해결에 필요한 충분한 정보를 포함함
- **SC-011**: 30분을 초과하는 작업이 자동으로 종료되고 랜디가 타임아웃 알림을 받음
- **SC-012**: 서버 재시작 후 랜디가 작업 중단 사실과 중단 시점 정보를 받음

## 가정사항

- 랜디는 텔레그램 계정을 가지고 있으며 직장에서 텔레그램에 액세스할 수 있음
- 랜디의 텔레그램 사용자 ID가 시스템 시작 시 환경 변수로 설정되어 있음
- 랜디는 리포지토리 액세스 권한과 GitHub Actions가 구성된 GitHub 계정을 가지고 있음
- CCW가 실행되는 원격 서버는 인터넷 연결과 GitHub 액세스 권한이 있음
- Claude Agent SDK를 사용할 수 있으며 이 사용 사례에 적절하게 라이선스되어 있음
- 랜디는 자동 커밋을 기대하는 대신 명시적 커밋 명령을 제공할 것임
- 시스템은 한 번에 하나의 작업만 실행하며, 작업 진행 중 새 요청은 거부됨
- 랜디는 작업 진행 중 메시지를 받으면 현재 작업이 완료될 때까지 기다릴 것임
- 시스템은 리포지토리의 `.ccw/logs/` 디렉토리에 대한 쓰기 액세스 권한을 가짐
- 작업 로그가 Git으로 추적되어 코드 변경사항과 함께 커밋됨
- 마크다운 형식이 작업 로그 문서화 요구사항에 충분함
- v1.0.0은 단일 GitHub 리포지토리에서만 작업함 (멀티 리포지토리 지원 제외)
